# Использование авторизации

### Для работы с API необходима JWT авторизация, для этого используй открытое api 
POST localhost:8080/api/auth/login

body:
{
"username":"Поросенок Петр",
"password":"password1"
}

из ответа необхоидмо скопировать значение ключа "accessToken", скажем это "eyABC" и при обращении ко всем API которые начинаются с /api/doc использовать header "Authorization" : "bearer eyABC".

### другие созданные рабочие учетки:
{"username": "Поросенок Петр", "password": "password1"}
{"username": "Колобок Виктор", "password": "password2"}
{"username": "Крокодил Гена", "password": "password3"}
{"username": "Еж Василий", "password": "password4"}
{"username": "Синица Николай", "password": "password5"} // system user (author by default)

p.s. если по какой-то причине юзеров нет, можно использовать апи быстрой регистрации нового пользака 

POST  localhost:8080/api/auth/register 

body:
{
"username":"New user",
"password":"password12345"
}

# Использование API
### 1. Создание документа
POST localhost:8080/api/doc/create

{
"name":"Документ ценообразования бензина"
}

### 2. Найти документ с историей по id


GET localhost:8080/api/doc/by-id/1, где 1 это id документа

### 3. Поиск документов по списку ids

POST localhost:8080/api/doc/search


{
"ids": [168203, 168352, 168353, 168354],
"staрtus": "DRAFT",
"authorId": 1,
"dateFrom": "2026-02-21T19:36:05.00",
"dateTo": "2026-02-21T22:55:01.00",
"page": 0,
"size": 30,
"sortBy": "name",
"sortDirection": "ASC"
}

*ids - обязательный параметр в теле запроса 

**поиск по дате обновления (трактовать все 3 варианта, либо поиск старше dateFrom, либо поиск моложе dateTo, либо поиск между dateFrom и dateTo)

### 4. Отправить на согласование (от 1 до 5000 шт)

# Опциональный блок
1. для обработки 5000+ запросов распилил лист ids на партиции, каждую партицию закинул в отдельный поток, кол-во потоков и объем документов на каждый поток регулируется в .yml файле. Например для 5000 документ, использовать 8 потоков по 625 документов в каждом (8*625 = 5000), или, на 8 потоков использовать 100-200 документов (по исследованию скорость не сильно меняется, потоки быстро перепрыгивают к последующей партиции).
2. если реестр утверждений не нужно связывать с документом, то лучше отдельная бд + отдельный сервис (из плюсов: пул соедининй с БД разгрузить и разгрузить кол-во действующих ядер на текущем сервере, но из минусов какая-то странная картина выходит, не исключена неконсистеность данных, надо усилинно продумать воркфлоу и краевые случаи). Если связывать реестр с документами, то лучше оставить одну БД (и надеяться, что максимальный пул соединений не лопнет), тогда в этом случае перекидываем нагрузку на другой серверок, который разгрузит основные потоки обработки данных.
